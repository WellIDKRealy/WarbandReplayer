Three databases. main is always present - the full
		multi-battle source, or (loading a single previously-exported battle
		directly) that one battle's data. r (Replay DB) is this
		battle's raw source rows, copied verbatim. b (Battle DB) is a
		derived roster/corpse snapshot. The dropdown above picks which one new
		bare table references target; you can always address any of them
		explicitly regardless of the dropdown, e.g. SELECT * FROM
		r.agent_states or SELECT * FROM b.roster_corpse_final.
		Replay DB/Battle DB always reflect whichever battle is currently active on
		the timeline, rebuilding automatically if you scrub to a different one.


		
Variables. Real SQL functions, usable anywhere a value works:

		
    
		    
  • CURRENT_TICK() - the tick currently on screen
    • 
		    
  • CURRENT_TIME() - current replay time within the active battle
    • 
		    
  • CURRENT_BATTLE() - active battle's faction text
    • 
		    
  • CURRENT_BATTLE_TICK_START() / CURRENT_BATTLE_TICK_END() - active battle's tick range
    • 
		    
  • CURRENT_BATTLE_ROWID_LO() / CURRENT_BATTLE_ROWID_HI() - active battle's agent_states rowid slice
    • 
		    
  • CURSOR_X() / CURSOR_Y() - world position of the crosshair fixed at screen center
    • 
		

		
Example: SELECT * FROM agent_states WHERE tick_id = CURRENT_TICK()


		
Live editing. Writes to main (e.g. UPDATE
		agent_states SET pos_x=... WHERE id=...) show up on the very next
		rendered frame - positions are read fresh from the table every frame,
		never cached. Editing ticks/events (tick timing,
		match boundaries) is not reflected - those are loaded once into
		memory at load time.


		
Generator scripts. Replay DB/Battle DB are built by real SQL too
		- open the Schema Explorer and click into r or b
		to see and edit the actual populate/derive query, with a Run and a Reset
		to default button. Rebuilds are smart: a view is only actually rebuilt
		when the active battle changes, the underlying data changes, or the
		generator script text itself changes (each tracked independently) -
		re-querying an unchanged view never redoes the work.
